# 协作项目提交平台需求规格说明

## 1. 项目背景

学生小组在完成课程作业、项目成果或实验任务时，通常需要多人分工协作。不同成员负责不同目录、模块或材料，最终由小组负责人统一整理并提交。

本平台用于支持小组成员上传源文件、协作维护项目目录、查看任务进度，并在项目完成后由负责人统一导出压缩包或生成邮件草稿进行提交。

本阶段只描述产品需求，不包含技术实现方案。

## 2. 项目目标

平台需要解决以下问题：

- 成员可以围绕同一个项目上传和维护源文件。
- 小组负责人可以管理项目成员、目录结构和最终提交内容。
- 文件不要求成员提前压缩，最终由负责人统一打包。
- 平台在最终打包前提供规则检查和清理建议。
- 平台支持导出最终压缩包，或生成带附件的邮件草稿。
- 平台记录上传、下载、整理、打包、邮件相关操作，方便小组内追踪。

## 3. 用户角色

### 3.1 小组负责人

小组负责人是项目的主要管理者。

小组负责人可以：

- 创建和管理小组。
- 删除小组（仅限小组内无项目时）。
- 创建和管理项目。
- 添加成员或生成邀请链接。
- 设置成员权限。
- 创建、移动、重命名和删除目录或文件。
- 查看项目进度。
- 查看操作记录。
- 执行打包前检查。
- 使用清理建议。
- 导出最终压缩包。
- 生成邮件草稿并确认发送。
- 将项目标记为结束。
- 重新打开已结束项目。

### 3.2 成员

成员参与一个或多个小组、一个或多个项目。

成员可以：

- 加入小组或项目。
- 查看自己有权限访问的项目内容。
- 上传文件。
- 下载项目内文件。
- 根据权限移动、重命名或删除目录中的文件。
- 查看全组操作记录。
- 标记有权限的任务或目录状态。
- 接收平台内通知。

### 3.3 只读用户

只读用户用于查看项目内容和进度。

只读用户可以：

- 查看文件列表。
- 查看项目进度。

只读用户不可以：

- 上传文件。
- 下载文件。
- 修改文件或目录。
- 查看操作记录。
- 执行检查、打包、导出或邮件相关操作。

## 4. 小组与项目

平台需要支持多个小组和多个项目。

- 不同小组之间的数据相互隔离。
- 一个成员可以加入多个小组。
- 一个成员可以参与多个项目。
- 用户进入平台后，应能明确选择当前小组或项目，避免误操作。
- 每个页面都应提供返回上一级的导航入口，让用户能在项目工作台、文件管理、进度、打包、邮件等页面间自由进退。
- 首页作为顶层页面，不需要返回上一级的入口。

小组删除规则：

- 只有小组负责人可以删除小组。
- 小组内存在项目时不允许删除，需要先删除所有项目。
- 删除小组会同时删除该组下的所有成员关系。
- 删除小组需要记录操作人。

首页应采用项目与小组结合的展示方式：

- 默认展示用户最近参与的项目。
- 项目卡片或项目列表展示项目名称、所属小组、进度状态和最近更新时间。
- 用户可以按小组筛选项目。

第一版需要支持基础搜索：

- 按项目名搜索。
- 按文件名搜索。
- 按成员名搜索。

## 5. 成员加入方式

平台支持两种加入方式：

1. 小组负责人手动添加成员。
2. 小组负责人生成邀请链接或邀请码，成员自行加入。

邀请链接或邀请码应支持两种模式：

- 直接加入：成员打开链接后可直接加入。
- 需要审核：成员申请加入后，需要小组负责人同意。

负责人在创建邀请时可以选择加入模式。

## 6. 权限规则

平台默认提供三种权限模板：

- 负责人
- 成员
- 只读

同时，负责人可以在默认模板基础上为成员单独调整权限。

可调整的权限包括但不限于：

- 查看
- 上传
- 下载
- 移动或重命名
- 删除
- 管理成员
- 执行检查
- 使用清理建议
- 打包导出
- 生成邮件草稿
- 发送邮件

文件下载规则：

- 成员可以下载项目内文件，便于协作。
- 只读用户不能下载文件。

文件删除规则：

- 成员可以删除自己有权限目录中的文件。
- 删除不只限制于自己上传的文件。
- 删除操作必须记录。
- 只读用户不能删除文件。

## 7. 项目目录与协作方式

平台采用混合协作模式：

- 负责人可以提前设置分工目录。
- 成员优先上传到自己负责或有权限的目录。
- 项目可以包含公共区域，用于存放资料、截图、参考素材、补充文件等。

所有文件都必须记录上传人，包括公共区域中的文件。

负责人可以在最终打包前手动整理文件结构，包括：

- 移动文件或目录。
- 重命名文件或目录。
- 删除无关文件。
- 整理最终目录结构。

负责人整理文件时，直接修改当前文件结构。成员看到的也是整理后的结果。

所有移动、重命名、删除和恢复操作都需要记录。

## 8. 文件上传与文件管理

成员上传文件时，可以上传源文件，也可以上传压缩包。

平台不禁止成员上传压缩包，但需要在最终检查时标记提醒。

同名文件重复上传时，平台应让上传者选择处理方式：

- 覆盖原文件。
- 重命名后上传。
- 保留为新版本。

平台第一版只需要展示文件列表和基本信息，不需要复杂文件预览。

文件基本信息包括：

- 文件名
- 文件大小
- 上传人
- 上传时间
- 所在目录
- 文件状态

## 9. 回收站

删除文件后，文件进入回收站，不直接永久删除。

回收站规则：

- 回收站文件不进入最终打包。
- 负责人可以查看和恢复全部回收站文件。
- 对原目录有权限的成员，可以查看和恢复该目录下被删除的文件。
- 删除和恢复都需要记录操作人和时间。
- 负责人可以清空回收站，永久删除回收站中所有文件。
- 清空回收站前必须弹窗确认，避免误操作。
- 清空回收站会永久删除文件，不可恢复。
- 清空回收站需要记录操作人和删除的文件数量。

## 10. 任务与进度

项目进度按任务或目录展示，不以成员为主要维度。

任务或目录状态包括：

- 未开始
- 进行中
- 已完成

状态标记规则：

- 负责人可以标记任意任务或目录状态。
- 有权限的成员可以标记自己负责或有权限的任务或目录状态。
- 状态变更需要记录操作人和时间。

成员可以标记自己的工作已完成，但该完成状态只是协作提示，不会锁定文件。

成员标记完成后，仍然可以继续上传或修改文件。

## 11. 打包前检查

最终打包前，平台需要提供规则检查。

检查内容包括：

- 是否所有必要目录已有文件。
- 是否存在空目录。
- 是否存在压缩包。
- 是否缺少必要说明文档。
- 是否存在缓存、临时产物或本地环境内容。
- 是否存在明显异常文件。

源码缓存内容检测应关注：

- 缓存目录。
- 临时文件。
- 日志文件。
- 系统生成的无关文件。
- 本地开发环境遗留内容。

检查结果只做提醒，不强制阻止打包。

负责人可以忽略风险继续打包。

## 12. 清理建议

打包检查界面需要提供风险项和一键清理建议。

清理建议只针对明显缓存或临时文件，不自动建议处理正常成果文件。

可建议清理的内容包括：

- `__pycache__/`
- `.DS_Store`
- `Thumbs.db`
- `*.tmp`
- `*.bak`
- `*.log`
- 临时缓存目录
- 系统生成的无关缓存文件

以下内容只提示风险，不进入一键清理建议：

- `.zip`、`.rar`、`.7z` 等压缩包。
- 空目录。
- 疑似重复文件。
- 无关大文件。
- 缺少说明文档。

负责人使用清理建议前，平台必须展示将被清理的文件或目录。

负责人可以选择清理部分风险项，也可以忽略风险继续打包。

## 13. 最终打包与导出

最终打包由负责人或有权限的成员执行。

最终压缩包采用直接放项目内容的结构。

示例：

```text
项目成果.zip
  前端/
  后端/
  报告/
  素材/
  README.md
```

压缩包中不额外套一层项目根目录。

最终导出格式支持：

- `.zip`
- `.7z`
- `.tar.gz`

负责人在打包前手动填写压缩包文件名。

文件名规则：

- 文件名不能为空。
- 文件名不能包含非法字符。
- 平台可以提示推荐命名格式，但不强制。

最终压缩包只保留最近一次。

- 每次重新打包后，会替换上一份可下载压缩包。
- 下载记录仍然保留。
- 如果覆盖旧压缩包，平台需要提醒负责人。

## 14. 邮件草稿与发送

平台支持生成邮件草稿，由负责人核实后再一键发送。

邮件草稿规则：

- 平台生成草稿，但不自动发送。
- 草稿包含收件人、主题、正文和最终压缩包附件。
- 负责人必须核实草稿后，才能主动点击发送。
- 发送动作必须由负责人主动触发。

收件人规则：

- 收件人由负责人每次手动填写。
- 平台不要求项目提前保存收件人。

邮件草稿生成后，负责人可以修改：

- 收件人
- 主题
- 正文
- 附件格式
- 附件对应的最终压缩包

邮件附件格式由负责人选择。

平台应提示：

- 推荐使用 `.zip` 作为邮件附件，兼容性最好。
- `.7z` 和 `.tar.gz` 也可作为附件格式。

## 15. 操作记录

平台需要记录关键操作。

记录范围包括：

- 上传记录
- 下载记录
- 文件移动记录
- 文件重命名记录
- 文件删除记录
- 文件恢复记录
- 任务或目录状态变更记录
- 打包记录
- 邮件草稿生成记录
- 邮件发送记录
- 项目结束记录
- 项目重新打开记录

上传记录应包含：

- 操作人
- 操作时间
- 文件名称
- 文件所在目录

下载记录应包含：

- 操作人
- 操作时间
- 下载对象
- 下载类型

打包记录应包含：

- 操作人
- 操作时间
- 压缩包名称
- 压缩包格式

邮件记录应包含：

- 草稿生成时间
- 草稿创建人
- 是否发送
- 发送时间

操作记录对小组内成员完全透明。

- 所有成员可以查看全部操作记录。
- 只读用户不能查看操作记录。

操作记录在项目结束后默认保留 30 天。

## 16. 项目结束与重新打开

项目支持结束状态。

项目结束方式：

- 成功导出压缩包或发送邮件后，平台可以提示负责人是否将项目标记为结束。
- 负责人也可以手动标记项目结束。

项目结束后：

- 项目默认锁定。
- 成员不能继续上传、整理或删除文件。
- 负责人可以重新打开项目，让项目回到可协作状态。
- 重新打开和再次结束都需要记录。

项目结束后，操作记录默认继续保留 30 天。

## 17. 通知

平台需要支持平台内通知。

通知范围按类型区分：

- 普通文件变化：通知相关目录有权限的成员和负责人。
- 目录状态变化：通知相关成员和负责人。
- 打包：通知全组成员。
- 邮件草稿生成：通知全组成员。
- 发送邮件：通知全组成员。
- 项目结束：通知全组成员。
- 权限或成员变更：通知受影响成员和负责人。

## 18. 暂不包含

第一版暂不包含以下能力：

- 截止时间管理。
- 复杂文件内容预览。
- 强制阻止打包。
- 以成员为主的项目进度视图。
- 长期保留多个历史压缩包。

## 19. 验收标准

### 小组管理补充验收

- 小组详情页有"删除小组"按钮。
- 非小组负责人不可见删除按钮。
- 小组内存在项目时删除被拒绝并提示。
- 删除前有确认弹窗。
- 删除后该小组从小组成员的小组列表中消失。

### 页面导航补充验收

- 所有子页面标题旁应显示返回箭头。
- 首页不显示返回箭头。
- 点击返回箭头回到正确上一级页面。
- 清空回收站前有确认弹窗。
- 清空后文件被永久删除，不可通过恢复功能找回。
- 操作记录中能查到清空回收站的记录和被删文件数量。

平台满足以下条件时，可认为第一版需求达成：

- 支持多个小组、多个项目。
- 成员可以加入多个小组和项目。
- 负责人可以手动添加成员，也可以生成邀请链接或邀请码。
- 邀请加入支持直接加入和需要审核两种模式。
- 支持负责人、成员、只读三种默认权限模板。
- 支持在模板基础上调整成员权限。
- 成员可以上传源文件，也可以上传压缩包。
- 同名文件上传时，可以选择覆盖、重命名或保留为新版本。
- 文件列表能展示基本信息。
- 删除文件进入回收站，且可按权限恢复。
- 项目进度按任务或目录展示。
- 任务或目录状态支持未开始、进行中、已完成。
- 打包前能执行规则检查。
- 检查结果只提醒，不阻止打包。
- 清理建议只针对明显缓存或临时文件。
- 最终压缩包不额外套项目根目录。
- 支持 `.zip`、`.7z`、`.tar.gz` 三种导出格式。
- 最终压缩包文件名由负责人手动填写。
- 平台只保留最近一次最终压缩包。
- 支持生成邮件草稿，并由负责人确认后发送。
- 上传、下载、整理、删除、恢复、打包、邮件等操作均有记录。
- 操作记录对成员透明，只读用户不可查看。
- 项目结束后默认锁定，负责人可以重新打开。
- 平台内通知能按操作类型发送给对应范围的成员。

## 20. 当前能力澄清与补充

本节用于对齐 2026-06-01 代码中已经补充或澄清的现有能力。后续开发、测试和接口整理应以本节与前文需求共同作为依据。

### 20.1 账号与个人中心

平台支持账号密码注册和登录。

注册信息包括：

- 用户名。
- 密码。
- 展示名称。
- 邮箱。

登录时可以使用用户名或邮箱作为账号。

登录成功后，前端保存当前用户摘要、开发阶段访问令牌和权限摘要。后端当前仍通过 `X-User-Id` 识别部分接口操作者，前端 HTTP 层会在登录后统一补充该请求头。

个人中心支持：

- 查看当前登录用户资料。
- 修改展示名称和邮箱。
- 修改密码。
- 管理当前用户自己的邮件发送配置。

### 20.2 SMTP 与邮件发送配置

平台的邮件发送能力以“平台内邮件草稿 + 用户自有 SMTP 配置发送”为当前主线。

SMTP 配置不再依赖固定的 `MAIL_HOST`、`MAIL_PORT` 等运行环境变量作为唯一来源。平台应支持将用户 SMTP 配置存入数据库，并通过个人中心界面动态管理，避免修改发送账号时必须重启服务。

用户可以在个人中心维护多套 SMTP 配置：

- 配置名称。
- SMTP 服务器地址。
- SMTP 端口。
- 登录账号。
- 登录密码。
- 发件人地址。
- IMAP 服务器地址。
- IMAP 端口。
- 是否启用 SSL。
- 是否启用 STARTTLS。
- 是否为默认配置。

SMTP 配置规则：

- 每套配置归属于创建用户。
- 用户只能查看、修改、删除和测试自己的 SMTP 配置。
- 同一用户可以设置一套默认 SMTP 配置。
- 发送邮件时可以显式选择 SMTP 配置。
- 未显式选择时，系统尝试使用当前用户默认 SMTP 配置。
- 如果没有可用配置，发送应失败并提示用户先配置 SMTP。
- SMTP 密码不得明文返回前端；后端存储时必须加密。
- 测试邮件必须由用户主动触发，不得在保存配置时自动发送。

SMTP 配置数据结构至少包含：

| 字段 | 规则 | 说明 |
| --- | --- | --- |
| `id` | 必填，系统生成 | SMTP 配置主键。 |
| `name` | 必填，同一用户下唯一 | 配置名称，例如“学校邮箱”或“个人邮箱”。 |
| `host` | 必填 | SMTP 服务器地址。 |
| `port` | 必填，默认 465 | SMTP 端口。 |
| `username` | 必填 | SMTP 登录账号。 |
| `password` | 必填，加密存储 | SMTP 登录密码或邮箱授权码。 |
| `from_address` | 必填 | 发件人地址。 |
| `ssl_enabled` | 必填，默认 true | 是否启用 SSL。 |
| `starttls_enabled` | 必填，默认 false | 是否启用 STARTTLS。 |
| `is_default` | 必填，默认 false | 是否为当前用户默认发件配置。 |
| `created_by` | 必填 | 配置创建用户。 |
| `created_at` | 必填，系统生成 | 创建时间。 |
| `updated_at` | 必填，系统维护 | 更新时间。 |

邮件草稿数据应记录可选的 `smtp_config_id`：

- 当草稿发送时显式选择 SMTP 配置，记录对应配置标识。
- 当 `smtp_config_id` 为空时，发送时使用当前用户默认 SMTP 配置。
- 已发送草稿应保留发送时选择的配置标识，便于后续追踪。

SMTP 配置接口至少包括：

| 方法 | 路径 | 功能 | 权限要求 |
| --- | --- | --- | --- |
| `GET` | `/smtp-configs` | 查询当前用户自己的 SMTP 配置列表 | 登录用户 |
| `POST` | `/smtp-configs` | 新增 SMTP 配置 | 登录用户 |
| `PUT` | `/smtp-configs/{id}` | 修改自己的 SMTP 配置 | 配置归属用户 |
| `DELETE` | `/smtp-configs/{id}` | 删除自己的 SMTP 配置 | 配置归属用户 |
| `POST` | `/smtp-configs/{id}/test` | 发送测试邮件 | 配置归属用户，且用户主动触发 |
| `PUT` | `/smtp-configs/{id}/default` | 设为默认配置 | 配置归属用户 |

SMTP 密码安全规则：

- 前端表单可以接收明文密码或邮箱授权码；生产环境必须通过 HTTPS 保障传输安全。
- 后端必须使用服务端密钥加密存储 SMTP 密码。
- 服务端密钥必须来自安全配置或环境变量，不得写入源码。
- 查询 SMTP 配置时不得返回明文密码，只能返回脱敏状态或固定掩码。
- 修改配置时，如果用户不填写新密码，应保留原加密密码。
- 测试发送、草稿发送失败时，错误信息不得包含明文密码、授权码或完整连接串。

邮件发送流程：

1. 用户在邮件草稿页点击发送，并明确确认发送动作。
2. 如果请求指定 `smtpConfigId`，后端加载该用户自己的对应 SMTP 配置。
3. 如果未指定 `smtpConfigId`，后端加载当前用户默认 SMTP 配置。
4. 如果没有可用配置，发送失败并提示用户先配置 SMTP。
5. 后端使用加载到的 SMTP 配置动态创建邮件发送客户端。
6. 发送成功后更新草稿状态、发送时间和操作记录。
7. 发送失败时草稿保持可编辑状态，并返回可理解的失败原因。

个人中心邮件设置交互规则：

- 个人中心应提供“邮件设置”入口。
- 配置列表应展示配置名称、服务器地址、端口、发件人地址和默认标识。
- 新增/编辑表单应包含名称、服务器地址、端口、账号、密码、发件人地址、SSL 开关和 STARTTLS 开关。
- 删除配置前必须弹窗确认。
- 用户可以主动发送测试邮件，并填写测试收件人地址。
- 用户可以将某一配置设为默认；设为默认后，同一用户的其他配置应取消默认状态。

邮件草稿发送交互规则：

- 邮件草稿发送确认区域应允许选择发件 SMTP 配置。
- 配置选项应展示配置名称和发件人地址，便于负责人确认发件身份。
- 默认选中当前用户的默认 SMTP 配置。
- 选择结果应作为 `smtpConfigId` 随发送请求提交。
- 未确认发送时，后端不得调用 SMTP 服务。

当前不把 QQ/163 等第三方邮箱草稿箱 API 作为必需能力。后续如要接入第三方草稿箱，应先补充独立需求。

SMTP 配置当前不包含：

- 第三方邮箱草稿箱 API 集成。
- 发送失败自动重试。
- SMTP 配置跨用户共享或权限分级。
- 密码的前端 RSA 加密。

### 20.3 邮件草稿总览与项目草稿

平台支持两个邮件草稿入口：

- 项目内邮件草稿页，用于指定项目的草稿创建、编辑、发送和删除。
- 邮件总览页，用于查看当前用户参与项目的草稿概览，并进入对应项目草稿。

邮件草稿发送时必须携带用户确认状态。未确认发送时，后端不得调用 SMTP 发送。

### 20.4 邀请加入

邀请链接作为成员加入项目的主要方式之一。

邀请加入支持：

- 直接加入。
- 申请后等待审核。

成员打开邀请链接后，应看到邀请所属小组、项目、加入模式和邀请状态。加入成功后跳转到项目工作台；等待审核时展示明确提示。

### 20.5 文件评论

项目文件支持评论能力。

评论规则：

- 用户可以查看指定文件的评论列表。
- 用户可以给指定文件添加评论。
- 评论作者可以删除自己的评论；具有管理权限的用户可以删除项目内评论。
- 评论内容应与文件标识绑定，不参与最终打包。

### 20.6 当前页面与路由口径

当前前端页面包括：

- 首页 `/`。
- 登录 `/login`。
- 注册 `/register`。
- 个人中心 `/profile`。
- 小组详情 `/groups/:groupId`。
- 项目工作台 `/projects/:projectId`。

任务进度当前以首页和项目工作台中的进度摘要为主，独立 `/projects/:projectId/progress` 页面暂不作为当前路由入口。

### 20.7 当前保留但前端入口不完整的能力

以下能力在后端或前端服务层已有接口基础，但当前页面入口可能尚未完整暴露：

- 文件移动。
- 目录状态更新。
- 加入申请审核通过或拒绝。
- 成员权限更新。
- 项目结束和重新打开。
- 压缩包历史列表和删除。

这些能力不视为无效需求。整理接口时不得仅因当前页面入口不完整而删除，除非先确认对应业务已不再需要。
