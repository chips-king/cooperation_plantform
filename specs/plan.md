# 分工协作系统技术落地计划

## 1. 文档目标

本文档基于 `specs/spec.md` 生成，用于指导后续任务拆分、接口设计、页面设计、测试设计和代码实现。

本文档不重新定义产品需求，只将已确认需求转化为可实现的系统方案。

需求追踪约定：

- `S1` 表示 `spec.md` 第 1 节。
- `S2` 表示 `spec.md` 第 2 节。
- 以此类推。

## 2. 总体架构

系统按业务能力拆分为以下模块：

| 模块 | 职责 | 追踪 |
|---|---|---|
| 身份与权限模块 | 用户身份、角色模板、自定义权限、访问控制 | S3, S5, S6 |
| 小组与项目模块 | 多小组、多项目、成员关系、项目状态 | S4, S5, S16 |
| 目录与文件模块 | 目录结构、文件上传、同名处理、文件信息、回收站 | S7, S8, S9 |
| 任务进度模块 | 按任务或目录展示状态，维护三态进度 | S10 |
| 检查与清理模块 | 打包前规则检查、缓存检测、清理建议 | S11, S12 |
| 打包导出模块 | 生成最终压缩包，保留最近一次导出 | S13 |
| 邮件草稿模块 | 生成草稿、修改草稿、确认发送 | S14 |
| 操作记录模块 | 上传、下载、整理、删除、恢复、打包、邮件等审计记录 | S15 |
| 通知模块 | 按操作类型发送平台内通知 | S17 |
| 搜索与首页模块 | 最近项目、小组筛选、项目/文件/成员搜索 | S4 |

建议采用分层结构：

```text
表现层
  页面、表单、弹窗、列表、状态反馈

应用层
  用例编排、权限检查、事务控制、操作记录、通知触发

领域层
  小组、项目、成员、目录、文件、任务状态、打包、邮件草稿等核心规则

基础设施层
  数据持久化、文件存储、压缩生成、邮件草稿服务、后台任务
```

关键原则：

- 所有写操作先做权限判断，再执行业务动作。
- 所有关键写操作成功后写入操作记录。
- 会影响成员感知的关键动作写入通知。
- 文件真实存储路径不得直接暴露给前端。
- 回收站文件、历史版本、最终压缩包应和普通项目文件区分管理。

## 3. 技术栈决策

本项目采用前后端分离的 Web 平台形态。

| 层级 | 技术选型 | 说明 | 追踪 |
|---|---|---|---|
| 前端框架 | Vue 3 + TypeScript | 用于构建多人协作、文件管理、权限配置、打包和邮件草稿等页面 | S3, S4, S7, S8, S13, S14 |
| 前端组件库 | Element Plus | 用于表格、表单、弹窗、上传组件、确认提示和后台管理界面 | S4, S6, S8, S11, S12 |
| 后端框架 | Java 17 + Spring Boot 3 | 用于实现用户、小组、项目、权限、文件、检查、打包、邮件和通知等服务 | S3-S17 |
| 权限控制 | Spring Security + 自定义权限表 | 支持负责人、成员、只读模板，以及成员级、目录级自定义权限 | S3, S6 |
| 数据库 | MySQL | 存储用户、小组、项目、权限、文件元数据、操作记录、通知和邮件草稿 | S3-S17 |
| 数据访问 | MyBatis-Plus | 用于实现常规 CRUD、分页查询和业务查询 | S3-S17 |
| 接口风格 | REST API | 前后端通过资源化接口交互，便于调试、测试和文档维护 | S4-S17 |
| 文件存储 | 本地存储 + 预留对象存储扩展 | 第一版文件保存在服务器本地，存储层保留后续切换 MinIO、OSS、COS 等对象存储的能力 | S7, S8, S9, S13 |
| 压缩处理 | 后端直接生成压缩包 | 后端负责生成 `.zip`、`.7z`、`.tar.gz`，避免依赖用户本地操作 | S13 |
| 邮件能力 | 第三方邮箱 API 草稿箱优先 | 优先面向 QQ 邮箱、163 邮箱等国内邮箱，目标是生成草稿并由负责人确认后发送 | S14 |
| 部署方式 | Docker Compose | 编排前端、后端、MySQL 和文件存储挂载目录，保证开发和部署环境一致 | S4, S8, S13 |
| 测试栈 | JUnit 5 + Vitest + Playwright | 后端单元/集成测试、前端组件测试和端到端流程测试 | S19 |

邮件能力存在技术风险：

- QQ 邮箱、163 邮箱等国内邮箱对“写入草稿箱”的开放 API 能力可能不统一。
- 实现前必须核实目标邮箱是否支持草稿箱 API 或等价能力。
- 如果目标邮箱不支持草稿箱 API，第一版降级为“平台内邮件草稿 + 授权后一键发送”。
- 邮箱授权信息必须安全保存，不得写入源码、配置文件或日志。

## 5. 权限模型

### 5.1 权限点

权限点应覆盖以下动作：

```text
project.view
project.manage
member.manage
permission.manage
file.view
file.upload
file.download
file.move
file.rename
file.delete
file.restore
directory.manage
directory.status.update
check.run
cleanup.apply
package.create
package.download
mail.draft.create
mail.draft.update
mail.send
log.view
notification.view
project.end
project.reopen
```

追踪：S3, S6, S7, S8, S9, S10, S13, S14, S15, S16, S17。

### 5.2 默认权限模板

负责人：

- 拥有项目内全部管理权限。
- 可管理成员、权限、目录、文件、检查、清理、打包、邮件、结束和重新打开项目。

成员：

- 可查看项目。
- 可上传文件。
- 可下载项目内文件。
- 可查看操作记录。
- 可在有权限目录内移动、重命名、删除和恢复文件。
- 可更新有权限目录状态。

只读：

- 只可查看文件列表和项目进度。
- 不可下载文件。
- 不可查看操作记录。
- 不可执行任何写操作。

### 5.3 权限执行规则

每个写接口必须执行：

1. 校验用户是否属于目标小组或项目。
2. 校验项目是否已结束。
3. 校验用户是否拥有动作权限。
4. 如果动作绑定目录，继续校验目录级权限。
5. 执行业务动作。
6. 写入操作记录。
7. 按规则发送通知。

项目结束后：

- 成员写操作全部拒绝。
- 负责人可以重新打开项目。
- 负责人重新打开后恢复协作能力。

追踪：S6, S16。

## 6. 主要业务流程

### 6.1 创建小组与项目

1. 负责人创建小组。
2. 负责人创建项目。
3. 负责人配置分工目录和公共目录。
4. 负责人添加成员或生成邀请。
5. 成员进入项目后选择对应小组和项目。

追踪：S4, S5, S7。

### 6.2 邀请加入

直接加入：

1. 成员打开邀请链接。
2. 系统校验链接有效。
3. 系统创建成员关系。
4. 写入操作记录。
5. 通知负责人和相关成员。

需要审核：

1. 成员打开邀请链接并提交加入申请。
2. 负责人收到审核通知。
3. 负责人同意或拒绝。
4. 同意后创建成员关系。
5. 写入操作记录。

追踪：S5, S15, S17。

### 6.3 上传文件

1. 成员选择目录。
2. 系统校验项目状态、用户权限和目录权限。
3. 系统检查文件名、大小、路径合法性。
4. 如存在同名文件，要求选择：
   - 覆盖原文件。
   - 重命名后上传。
   - 保留为新版本。
5. 保存文件。
6. 写入上传记录。
7. 通知相关目录有权限成员和负责人。

追踪：S8, S15, S17。

### 6.4 删除与恢复文件

删除：

1. 用户选择文件。
2. 系统校验项目状态和目录删除权限。
3. 文件状态变为回收站。
4. 写入删除记录。
5. 通知相关成员。

恢复：

1. 用户进入回收站。
2. 系统只展示有权限恢复的文件。
3. 用户选择恢复。
4. 文件回到原目录，若原目录不存在，需要提示选择恢复目录。
5. 用户选择新的恢复目录后，文件的所属目录应更新为该目录。
6. 写入恢复记录，并在记录元数据中保存恢复目录标识。
7. 通知相关成员。

追踪：S9, S15, S17。

### 6.5 目录状态维护

1. 用户进入任务或目录进度视图。
2. 用户选择状态：未开始、进行中、已完成。
3. 系统校验状态更新权限。
4. 更新目录状态。
5. 写入状态变更记录。
6. 通知相关成员和负责人。

追踪：S10, S15, S17。

### 6.6 打包前检查

1. 用户点击打包前检查。
2. 系统扫描当前项目文件树。
3. 生成检查报告：
   - 空目录。
   - 压缩包。
   - 缺少必要说明文档。
   - 缓存或临时文件。
   - 本地环境遗留内容。
   - 明显异常文件。
4. 系统生成清理建议，仅覆盖明显缓存或临时文件。
5. 检查结果展示给用户。
6. 检查结果不阻止打包。

追踪：S11, S12。

### 6.7 应用清理建议

1. 用户查看建议清理列表。
2. 系统展示将被处理的文件或目录。
3. 用户可先生成清理预览，预览只返回对象列表，不改变文件状态、不保存清理结果。
4. 用户选择部分或全部清理项。
5. 系统校验清理权限。
6. 将清理对象移入回收站或标记为已清理。
7. 写入操作记录。
8. 通知相关成员。

建议：清理建议采用“移入回收站”方式，避免误删。

追踪：S12, S9, S15, S17。

### 6.8 最终打包

1. 用户进入打包页面。
2. 用户填写压缩包文件名。
3. 用户选择格式：`.zip`、`.7z`、`.tar.gz`。
4. 系统提示是否会覆盖最近一次压缩包。
5. 系统执行打包前检查并展示结果。
6. 用户可继续打包。
7. 系统按当前项目内容生成压缩包。
8. 系统记录文件树快照时间 `snapshot_created_at`，压缩请求、压缩结果和打包记录均应携带该时间。
9. 压缩包内部直接放项目内容，不额外套一层项目根目录。
10. 标记为最近一次压缩包。
11. 写入打包记录。
12. 通知全组成员。

排除范围：

- 回收站文件。
- 旧的最终压缩包。
- 系统内部元数据。
- 未恢复的清理项。

追踪：S11, S12, S13, S15, S17。

### 6.9 邮件草稿与发送

生成草稿：

1. 用户选择最近一次压缩包或触发重新打包。
2. 用户填写收件人。
3. 系统生成邮件主题、正文和附件。
4. 草稿创建结果应返回附件展示文件名，便于前端核对最终压缩包。
5. 用户可修改收件人、主题、正文、附件格式和附件。
6. 保存为草稿。
7. 写入草稿生成记录。
8. 通知全组成员。

发送邮件：

1. 用户打开草稿。
2. 用户核对内容。
3. 用户主动点击发送并完成确认。
4. 发送命令必须携带确认标记 `confirmed`，未确认时不得调用邮箱发送端口。
5. 系统发送邮件。
6. 写入发送记录。
7. 通知全组成员。
8. 成功后提示是否结束项目。

追踪：S14, S15, S16, S17。

### 6.10 项目结束与重新打开

结束：

1. 负责人手动结束，或导出/发送成功后按提示结束。
2. 项目状态变为已结束。
3. 成员写操作锁定。
4. 应用层通过写锁端口锁定项目写操作。
5. 写入结束记录。
6. 通知全组成员。
7. 操作记录保留到期时间设置为结束后 30 天。

重新打开：

1. 负责人点击重新打开。
2. 项目状态变为协作中。
3. 应用层通过写锁端口恢复项目写操作。
4. 写入重新打开记录。
5. 通知全组成员。

追踪：S16, S15, S17。

## 7. 页面规划

页面导航规则：

- 首页（/）是顶层页面，不提供返回入口。
- 每个子页面应在标题左侧提供返回箭头。
- 返回优先级：浏览器历史回退 > 按路由层级跳转。
- 项目子页面（文件管理、任务进度、打包检查、打包导出、邮件草稿、操作记录）返回目标为项目工作台。
- 项目工作台返回目标为首页。
- 小组详情页返回目标为首页。
- 通知中心返回目标为首页。

## 9. 文件存储与路径规则

### 9.1 存储分区

建议逻辑上拆分为：

```text
project-files/
trash/
packages/
mail-attachments/
```

业务规则：

- 普通项目文件只从 `project-files` 参与最终打包。
- 回收站文件不进入打包。
- 最终压缩包放入 `packages`。
- 邮件附件引用最终压缩包，不复制成员源文件。

追踪：S8, S9, S13, S14。

### 9.2 路径安全

所有文件操作必须基于内部文件标识，不允许前端直接提交真实存储路径。

文件名校验：

- 不允许空文件名。
- 不允许路径分隔符。
- 不允许 `../`、`..\`。
- 不允许系统根路径形式。
- 不允许控制字符。

追踪：S8, S11, S13。

### 9.3 同名文件策略

同名文件上传时必须显式选择策略：

```text
overwrite
rename
new_version
```

覆盖：

- 原文件状态变为 `superseded` 或进入历史版本。
- 新文件成为当前文件。

重命名：

- 用户指定新名称或系统建议名称。
- 不影响原文件。

保留为新版本：

- 新文件与旧文件共用 `version_group_id`。
- 当前文件列表展示最新版本。
- 历史版本可在文件详情中查看。

追踪：S8。

## 11. 打包规则设计

打包输入：

- 当前项目文件树。
- 仅包含状态为 `active` 的文件。
- 排除回收站文件。
- 排除系统内部文件。
- 排除旧压缩包。

打包输出：

- `.zip`
- `.7z`
- `.tar.gz`

打包结构：

```text
压缩包名
  目录A/
  目录B/
  文件C
```

不额外创建项目根目录。

覆盖策略：

- 系统仅保留最近一次最终压缩包。
- 新包生成前提示会覆盖旧包。
- 新包生成成功后，旧包不再作为最新包展示。
- 历史下载记录继续保留。

追踪：S13, S15。

## 12. 邮件草稿规则设计

邮件草稿应与最终压缩包绑定。

生成草稿前：

- 必须存在可用最终压缩包，或引导先打包。
- 收件人由负责人手动填写。
- 附件格式可选择，但提示推荐 `.zip`。

草稿可修改：

- 收件人。
- 主题。
- 正文。
- 附件格式。
- 附件对应压缩包。

发送前：

- 必须展示最终确认。
- 必须由用户主动触发。

发送后：

- 更新草稿状态。
- 写入邮件发送记录。
- 通知全组成员。
- 提示是否结束项目。

追踪：S14, S15, S16, S17。

## 14. 异常与边界场景

### 14.1 权限变化

场景：

- 成员正在上传时权限被移除。
- 成员正在打包时项目被结束。

处理：

- 写操作提交时必须重新校验权限和项目状态。
- 前端展示权限变化后的可用操作。

追踪：S6, S16。

### 14.2 目录被移动或删除

场景：

- 用户上传目标目录已被负责人移动。
- 恢复文件时原目录已不存在。

处理：

- 上传前刷新目标目录状态。
- 恢复时提示选择新的恢复目录。

追踪：S7, S9。

### 14.3 同名冲突

场景：

- 多成员同时上传同名文件。

处理：

- 以最终写入时的目录状态为准检测冲突。
- 如冲突出现，返回同名处理选项。

追踪：S8。

### 14.4 打包期间文件变化

场景：

- 打包开始后有人上传或删除文件。

处理：

- 打包时生成文件树快照。
- 压缩包基于快照生成。
- 打包记录中记录快照时间。

追踪：S13, S15。

### 14.5 邮件发送失败

场景：

- 邮件服务失败。
- 附件不可用。
- 收件人格式错误。

处理：

- 草稿保持未发送状态。
- 展示明确失败原因。
- 不自动重复发送。
- 用户修正后可再次发送。

追踪：S14。

## 19. 小组删除实现说明

### 19.1 小组删除规则

- 只有小组负责人可以删除小组。
- 小组内存在项目时不允许删除。
- 删除小组时级联删除该小组的成员关系。
- 删除操作需要记录。

### 19.2 相关接口

```text
DELETE /groups/{groupId}
```

请求头：`X-User-Id` 当前操作人标识。

响应：
```json
{
  "deletedGroupId": 123
}
```

### 19.3 实现步骤

1. GroupRepository 新增 `deleteById` 方法。
2. MembershipRepository 新增 `deleteByGroupId` 方法。
3. 创建 `DeleteGroupUseCase`：
   - 校验操作人为小组负责人。
   - 校验小组内项目数量为 0。
   - 删除成员关系。
   - 删除小组。
   - 写入操作记录。
4. GroupController 新增 `DELETE /groups/{groupId}`。
5. 前端新增 `deleteGroup` API 和删除按钮。
